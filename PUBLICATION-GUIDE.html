Publier SecureCode AI en open source, sans en perdre le contrôle

Ce guide couvre, dans l'ordre, la création du dépôt public, le verrouillage de la branche main pour qu'aucune modification externe ne s'applique sans ta revue, le cadre de contribution pour les devs et vibe coders, et l'installation du skill dans un agent de code (Claude Code, Cursor, Codex, Windsurf).

Avant tout

Les mots à connaître

Tu n'as jamais utilisé GitHub — voici exactement ce que veut dire chaque terme employé dans ce guide, dans l'ordre où tu vas les rencontrer.

Git
Le logiciel installé sur ton ordinateur qui garde en mémoire chaque version de tes fichiers au fil du temps. Il fonctionne même sans connexion internet — c'est un carnet de versions local.
GitHub
Le site web (github.com) qui héberge en ligne une copie de ce carnet Git, pour que d'autres personnes puissent le consulter, le télécharger, ou proposer des changements. Git est l'outil, GitHub est l'endroit où tu le mets en ligne.
Dépôt (repo)
Le dossier complet de ton projet, une fois mis en ligne sur GitHub. Le tien s'appellera securecode-ai et contiendra tous les fichiers que tu as déjà construits.
Commit
Une "photo" d'un ensemble de changements, avec un message qui explique ce qui a changé et pourquoi. Ton premier commit contiendra tout le skill tel qu'il existe aujourd'hui.
Branche (main)
Une ligne de développement indépendante. main est la branche par défaut — celle que voit tout le monde qui visite ton dépôt. C'est elle qu'on va protéger.
Fork
Quand quelqu'un d'autre clique sur "Fork" sur ton dépôt, GitHub lui crée sa propre copie complète, sous son compte. Il modifie sa copie — jamais la tienne directement.
Pull Request (PR)
Une fois que ce quelqu'un a modifié sa copie (son fork), il t'envoie une demande : "voici ce que j'ai changé, veux-tu l'intégrer chez toi ?" C'est une proposition, jamais une modification automatique.
Merge (fusion)
Le moment où toi — et personne d'autre si la protection est activée — acceptes la Pull Request et l'intègres réellement dans ton dépôt. Avant ce clic, rien n'a changé chez toi.
Ce qu'il faut retenir de tout ça Le chemin d'une contribution externe est toujours : fork → modification chez l'autre → Pull Request → ta lecture → ton clic "Merge". Il n'existe aucun raccourci qui saute ton clic final, une fois la protection de branche activée (étape 3).
Avant de commencer

Ce que ce guide suppose déjà en place

Un compte, un logiciel, dix minutes. Le CLI (gh) est optionnel — chaque étape qui l'utilise a son équivalent au clic sur le site web.

1
Crée ton compte GitHub si tu n'en as pas déjà un : va sur github.com/signup, choisis un nom d'utilisateur (ce sera visible dans les liens de ton projet, ex. github.com/ton-pseudo/securecode-ai), une adresse e-mail, un mot de passe. Confirme l'e-mail reçu.
2
Installe Git sur ta machine (le logiciel local, différent du site) : git-scm.com/downloads, version Windows, installation avec les options par défaut. Vérifie ensuite dans un terminal (PowerShell) : 
git --version
3
Dis à Git qui tu es — la première fois seulement, ces informations s'attachent à chacun de tes commits : 
git config --global user.name "Ton Nom"
git config --global user.email "ton-email@exemple.com"
4
(Optionnel) Installe GitHub CLI — gh permet de créer le dépôt et ses règles de protection sans quitter le terminal : cli.github.com, puis gh auth login et suis les instructions (choisis GitHub.com → HTTPS → Login with a web browser). Si tu préfères tout faire au clic sur le site, passe cette étape — ce guide donne les deux chemins partout où gh apparaît.
Ouvre PowerShell, pas l'Invite de commandes Windows propose deux terminaux différents. L'Invite de commandes (fenêtre noire, l'invite ressemble à C:\laragon\www\skils>) ne comprend pas la syntaxe utilisée par la plupart des outils en ligne de commande modernes. Utilise PowerShell à la place : dans l'Explorateur de fichiers, ouvre le dossier security-ai-skill, Shift + clic droit dans un espace vide → Ouvrir la fenêtre PowerShell ici (ou Ouvrir dans le terminal selon ta version de Windows). L'invite ressemble alors à PS C:\laragon\www\skils\security-ai-skill>. Toutes les commandes de ce guide sont écrites pour PowerShell.
Point de départ Toutes les commandes ci-dessous partent du dossier c:/laragon/www/skils/security-ai-skill/ — le contenu du skill est déjà complet (base de connaissance, règles, prompts, exemples). Ce guide ne touche pas à ce contenu, il ne fait que le publier correctement.
Étape 1

Préparer le dépôt local

Initialiser git et exclure ce qui ne doit jamais quitter ta machine.

Le dossier n'est pas encore un dépôt git. On l'initialise, on ajoute un .gitignore, et on fait le premier commit.

terminal 
cd security-ai-skill
git init
git branch -M main

Crée un fichier .gitignore à la racine :

.gitignore 
# Environnements locaux
.env
.env.*
node_modules/
__pycache__/
*.pyc

# Registre zero-day — appartient au projet AUDITÉ, jamais à ce skill
.securecode/

# Fichiers d'éditeur
.vscode/
.idea/
.DS_Store
Thumbs.db
Vérification avant le premier commit Relis git status avant d'ajouter quoi que ce soit. Ce skill ne contient normalement aucun secret réel — les exemples utilisent des placeholders (REPLACE_WITH_YOUR_API_KEY, etc.) — mais c'est le seul moment où une clé oubliée dans un fichier de test passerait inaperçue pour toujours.
terminal 
git add .
git status              # relire la liste avant de commiter
git commit -m "Initial commit — SecureCode AI Enterprise Skill v0.2.0"
Étape 2

Créer le dépôt GitHub

Deux façons d'arriver au même résultat — choisis celle où tu es à l'aise.

Option A — au clic, depuis github.com (recommandé, aucun outil à installer)

1
Connecté sur github.com/new, remplis : Repository name → securecode-ai. Description → « Skill de sécurité applicative pour agents de code IA (Claude Code, Cursor, Codex) — détection, explication, correction et scoring OWASP/ASVS. ». Sélectionne Public. Ne coche aucune case ("Add a README", ".gitignore", "license") — tes fichiers existent déjà localement, cocher ces cases créerait un conflit inutile. Clique Create repository.
2
GitHub affiche une page "Quick setup" avec une section "…or push an existing repository from the command line" — elle contient deux commandes toutes prêtes, avec ton pseudo déjà inclus. Copie-les telles quelles depuis cette page (elles sont plus fiables que celles recopiées d'un guide), colle-les dans PowerShell (voir l'encadré ci-dessus), une ligne à la fois : 
git remote add origin https://github.com/ton-pseudo/securecode-ai.git
git push -u origin main

PowerShell te demandera peut-être de te connecter à GitHub à ce moment — une fenêtre de navigateur s'ouvre, clique Authorize, reviens au terminal.

Option B — en une commande, avec GitHub CLI

Si tu as installé gh (étape 0, point 4) :

terminal 
gh repo create securecode-ai --public --source=. --remote=origin --push

Cette seule commande crée le dépôt sur GitHub, l'associe à ton dossier local, et envoie ton premier commit — tout en une fois. Ajoute la description ensuite sur la page du dépôt (bouton engrenage ⚙️ à côté de "About", en haut à droite de la page).

Une fois le push terminé (par l'une ou l'autre option), actualise la page du dépôt : tes dossiers knowledge/, rules/, examples/… apparaissent. Active ensuite dans Settings → General → Features :

  • Issues — pour que les devs signalent des faux positifs, des CWE mal mappés, ou proposent une catégorie manquante.
  • Discussions — pour les questions d'usage qui ne sont pas des bugs.
  • Preserve this repository (GitHub Archive Program) — optionnel, mais cohérent pour un projet destiné à durer.

Étape 3 — le cœur de la sécurité du dépôt

Verrouiller main avant toute chose

Aucune modification, d'où qu'elle vienne, ne doit atteindre main sans passer par ta revue.

Ce qui te protège réellement, avant même cette étape Un inconnu sur internet n'a jamais la permission d'écrire directement dans ton dépôt — seul un compte que tu ajoutes explicitement comme collaborateur l'a. Pour tout le monde d'autre, le seul chemin possible est déjà fork → Pull Request → ton clic "Merge" (glossaire ci-dessus), même sans aucune règle en plus. Cette étape 3 ajoute un filet de sécurité supplémentaire : elle t'oblige toi aussi à passer par une PR plutôt qu'un push direct — une discipline utile, mais pas la barrière principale contre un acteur malveillant.

GitHub appelle cette règle une règle de protection de branche.

Chemin pour y arriver au clic : sur la page de ton dépôt → onglet Settings (en haut, tout à droite) → dans le menu de gauche, Branches → bouton Add branch protection rule (ou Add rule). Dans le champ Branch name pattern, tape main. Coche ensuite les cases du tableau ci-dessous, puis Create en bas de page.

Suis le chemin au clic ci-dessus Il existe une version en une seule commande gh api ... pour ce réglage, mais elle est fragile à recopier correctement dans un terminal Windows (guillemets, crochets). Vu que gh n'est de toute façon pas indispensable pour publier ce dépôt, ce guide ne la détaille pas — le chemin au clic ci-dessus donne exactement le même résultat, de façon plus fiable.
Case à cocherEffet
Require a pull request before mergingPlus aucun push direct sur main — même pour toi
Require approvals → 1Une PR ne se merge pas sans une revue explicite
Dismiss stale approvals on new commitsUn dernier commit ajouté après approbation redemande une revue
Require review from Code OwnersVoir CODEOWNERS ci-dessous — une PR touchant rules/, prompts/ ou SKILL.md te désigne automatiquement comme relecteur
Allow force pushes → désactivéL'historique de main ne peut pas être réécrit
Allow deletions → désactivémain ne peut pas être supprimée accidentellement ou malicieusement
Ne coche pas "Do not allow bypassing the above settings" Cette case appliquerait la règle même à toi en tant qu'administrateur — en solo, "Require approvals: 1" te bloquerait alors toi-même, puisque personne d'autre ne peut approuver ta propre PR. Laisse-la décochée : les contributeurs externes restent entièrement bloqués (ils n'ont jamais la permission d'écrire directement, voir ci-dessus), et toi seul gardes la possibilité de fusionner tes propres correctifs sans attendre une deuxième personne. Si tu ajoutes un jour un co-mainteneur de confiance avec accès en écriture, reviens cocher cette case à ce moment-là.

CODEOWNERS — toi comme dernier verrou sur le contenu sensible

Ce fichier force ta revue spécifiquement sur les dossiers qui définissent le comportement de l'agent — les contributions sur examples/ ou docs/ restent plus légères à approuver, celles sur rules/, prompts/, ou SKILL.md ne peuvent jamais te contourner.

.github/CODEOWNERS 
# Toute PR nécessite ta revue par défaut
* @ton-pseudo-github

# Le comportement de l'agent — jamais mergé sans ta revue explicite
/SKILL.md @ton-pseudo-github
/rules/ @ton-pseudo-github
/prompts/ @ton-pseudo-github
/schemas/ @ton-pseudo-github

Pour créer ce fichier sans terminal : sur la page du dépôt, clique Add file → Create new file, tape .github/CODEOWNERS comme nom (le / crée automatiquement le dossier), colle le contenu ci-dessus en remplaçant @ton-pseudo-github par ton pseudo réel, puis Commit changes directly to the main branch en bas de page — cette action reste possible même une fois la protection activée, car GitHub te reconnaît comme le propriétaire ; un contributeur externe, lui, ne verra jamais ce bouton.

Pourquoi ça bloque vraiment les mauvaises manipulations Un contributeur malintentionné peut toujours proposer une règle de détection affaiblie ou un prompt qui pousse l'agent à ignorer une catégorie de vulnérabilité — mais sa PR reste une proposition tant que tu ne l'as pas fusionnée. Rien de ce qu'il écrit n'atteint quiconque installe le skill avant ta relecture ligne à ligne.
Étape 4

Le cadre de contribution

Ce que voit un dev qui veut proposer une amélioration.

CONTRIBUTING.md existe déjà dans le dépôt et décrit le gabarit attendu pour une nouvelle entrée knowledge/ ou rules/. Ajoute en tête de ce fichier le rappel explicite du flux — c'est la phrase que chaque contributeur doit lire avant d'ouvrir une PR :

CONTRIBUTING.md — à ajouter en introduction 
## Flux de contribution

Ce dépôt n'accepte aucune modification directe sur `main`. Toute
contribution passe par une Pull Request depuis un fork, et n'est
fusionnée qu'après revue explicite d'un mainteneur — jamais
automatiquement, quel que soit l'état des vérifications automatiques.

1. Fork du dépôt, branche dédiée (`feat/xxe-rust-example`,
   `fix/cwe-mapping-idor`, ...).
2. Une PR par sujet — pas de PR qui mélange dix vulnérabilités
   différentes, ça ralentit la revue et retarde ta contribution.
3. Respecte le gabarit de la vulnérabilité concernée (voir plus bas) :
   CWE réel et vérifié, portée strictement défensive, pas de payload
   d'exploitation fonctionnel.
4. Un mainteneur revoit, demande des ajustements si besoin, fusionne.
   Aucune contribution n'est appliquée sans cette étape.

Étape 5

Fichiers communautaires à finaliser

Deux fichiers doivent être une vraie décision, pas un gabarit oublié.

LICENSE.md

LICENSE.md contient déjà une proposition de licence commerciale (usage autorisé sans redistribution des règles). C'est une proposition à valider avant publication, pas un texte prêt à l'emploi — relis-le et décide explicitement :

  • Le code source du skill est-il librement redistribuable (MIT/Apache-2.0), ou seulement son usage (licence propriétaire avec clause d'attribution) ?
  • Si tu comptes vendre une version premium ailleurs (Capafy, voir SPEC.md section 10), le dépôt public doit rester cohérent avec cette distinction — ne publie pas en MIT un contenu que tu comptes vendre ensuite sous licence fermée.

SECURITY.md — signalement de vulnérabilité, pour ce dépôt lui-même

Un skill de sécurité qui n'a pas sa propre procédure de signalement responsable est incohérent avec son propre objet. Ajoute :

SECURITY.md 
# Signalement de vulnérabilité

Si tu identifies une vulnérabilité dans le moteur du skill lui-même
(par exemple une règle qui masquerait un pattern dangereux, ou une
faille dans le format des schémas permettant une injection dans le
pipeline de patch), signale-la en privé via l'onglet **Security**
de ce dépôt GitHub (Security → Report a vulnerability), pas via une
issue publique.

Pour un faux négatif ou un faux positif ordinaire sur une règle de
détection, une issue publique classique convient.

Même méthode que pour CODEOWNERS : Add file → Create new file, nom SECURITY.md, colle, Commit changes. Une fois ce fichier présent, l'onglet Security du dépôt propose automatiquement Report a vulnerability aux visiteurs.

Étape 6

Publier

Dans l'ordre — l'ordre évite de pousser sur une branche pas encore protégée.

  1. Étape 1 (init local) → Étape 2 (créer + premier push) — main existe désormais côté GitHub, encore non protégée.
  2. Étape 3 immédiatement après — protège main avant qu'un tiers ait eu la moindre chance d'y accéder.
  3. Ajoute CODEOWNERS, SECURITY.md, la mise à jour de CONTRIBUTING.md via une PR normale (même toi tu passes maintenant par ce chemin — c'est la preuve que la protection fonctionne).
  4. Ajoute les topics GitHub du dépôt (Settings → topics) : security, ai-agent, claude-code, sast, owasp — c'est ce qui te rend trouvable par les devs qui cherchent.
Installation

Utiliser le skill dans un agent de code

Le point d'entrée est toujours SKILL.md — chaque agent le charge différemment.

Commandes ci-dessous en PowerShell Mêmes règles qu'à l'étape 0 : ouvre PowerShell dans le dossier de ton projet (celui où tu veux utiliser le skill — pas security-ai-skill/ lui-même), pas l'Invite de commandes.

Claude Code dossier de skill

Claude Code charge automatiquement tout skill placé dans .claude/skills/, à la racine du projet.

git clone https://github.com/ton-pseudo/securecode-ai .claude/skills/securecode-ai

Claude Code détecte le skill au prochain lancement — il se déclenche automatiquement selon la description de SKILL.md, ou explicitement via /securecode-ai.

Cursor règle de contexte

Cursor n'a pas de notion native de "skill" — on référence le skill comme règle de projet toujours chargée.

git clone https://github.com/ton-pseudo/securecode-ai vendor/securecode-ai
mkdir .cursor\rules

Puis crée le fichier .cursor/rules/securecode-ai.mdc (dans ton éditeur, ou Add file → Create new file si le projet est aussi sur GitHub) avec ce contenu :

.cursor/rules/securecode-ai.mdc 
---
description: Sécurité applicative — SecureCode AI
alwaysApply: true
---
Charge et applique le skill décrit dans
vendor/securecode-ai/SKILL.md pour toute tâche
touchant à la sécurité du code.

Codex (CLI / IDE) AGENTS.md

Codex lit AGENTS.md à la racine du projet comme instruction système persistante.

git clone https://github.com/ton-pseudo/securecode-ai vendor/securecode-ai

Puis ouvre (ou crée) AGENTS.md à la racine du projet et ajoute à la fin :

AGENTS.md — à la suite du fichier existant 
## Sécurité
Suis le skill vendor/securecode-ai/SKILL.md pour tout
code touchant à l'authentification, aux entrées
utilisateur, ou à la configuration cloud/Docker.

Windsurf / autre agent fallback universel

Pour un agent sans mécanisme de règle persistante, colle directement le contenu de SKILL.md en tout début de session — le fichier est conçu pour ça : frontmatter + workflow autonome.

git clone https://github.com/ton-pseudo/securecode-ai vendor/securecode-ai
Get-Content vendor/securecode-ai/SKILL.md

Copie ce que la commande affiche, colle-le comme premier message ou instruction système de la session.

Ce que ça donne une fois installé
